# CarbonJ Content Design

把同一条视频转成七套平台原生内容。不要把一份通稿机械缩写或改写七次。

## 输入

至少需要以下一种可靠语料：

- 视频及其同名 `.srt` / `.ass` 字幕；
- 视频及用户指定的口播稿；
- 无视频时，用户明确提供的完整文稿。

收到视频或字幕路径后，先运行：

```bash
python3 scripts/discover_input.py --input "<视频或SRT路径>"
```

视频入口会自动寻找同名 `.srt` / `.ass`；SRT 入口会自动寻找同目录、同 stem 的 `.mp4` / `.mov` / `.m4v`。两者同时存在时，字幕负责语义和事实，视频负责时长、画幅、画面证据和可靠章节时间；不能用画面猜测代替字幕内容。只有字幕也可以生成七平台内容预览。

若找到多个可能的字幕、视频或口播稿，优先使用 stem 完全一致的组合；仍有歧义时再询问。

默认生成全部七个平台；用户明确指定平台时只生成所选平台。可选输入包括目标受众、主打角度、行动引导、语言和希望强调的结果。

## 工作流

1. 解析字幕时间轴并通读字幕或口播稿；有视频时同时检查视频元数据和代表性画面。建立 `contentBrief`：主题、受众、痛点、操作、结果、证据和禁用表述。
2. 区分三类陈述：素材直接支持的事实、需要注明来源的自报/第三方说法、无法确认的推测。不得把后两类改写成确定事实。
3. 先确定一个共同选题，再按平台重新组织标题、正文和标签。小红书生成的是发布搜索标题，不是封面标题；正文约 200 字并自然覆盖搜索词。抖音只生成标题和话题，不生成正文。视频号生成短标题、核心理论和结构化长简介。
4. 生成前阅读 [references/voice.md](references/voice.md)、[references/platform-rules.md](references/platform-rules.md) 和 [references/output-schema.md](references/output-schema.md)。平台规则中的硬约束必须满足，策略建议可以按视频内容调整。
5. 在临时目录中组织符合 schema 的 JSON，仅用于校验和渲染；它不是交付物。运行：

```bash
python3 scripts/validate_package.py "/tmp/<临时内容包>.json" \
  --preview-output "<输入文件所在目录>/<输入stem>_七平台内容预览.md"
```

6. 默认只保留并交付 `<输入stem>_七平台内容预览.md`。验证失败时只修正对应字段；不要为了通过检查而改变视频事实。预览必须写入七个平台的完整成品文案，不能用“本视频主要讲了……”之类的概述代替正文。

只有用户明确要求发布兼容包时，才额外运行 `--publisher-output`。用户明确要求 JSON、事实底稿或其他中间文件时，才将相应文件保留下来。

## 输出边界

- 默认交付物只有一个 Markdown：`<输入stem>_七平台内容预览.md`，直接放在输入视频或字幕旁边。
- 默认不创建 `.content-design` sidecar 目录，不留下 `content-package.json`、`source-analysis.json`、`video-publisher-package.json` 或其他中间文件。
- 小红书、抖音、B站、视频号的兼容发布包只在用户明确要求时生成，用于交给 `video-publisher` 做后续草稿准备。
- 本 Skill 不自动打开创作者后台，不上传草稿，不点击任何发布按钮。
- 第一版不制作封面、不生成视频字幕、不联网补充事实。素材不足时明确标记 `needs_user_confirmation`，不要编造。
- 所有话题或 hashtag 在内容包和预览中都以 `#` 开头，多个话题之间只用空格，不用顿号；转换为平台发布包时再按适配器需要自动去掉 `#`。

## 完成标准

- 默认预览中七个平台字段齐全；用户明确指定平台时与其选择一致；
- 标题、正文、标签分开；
- 小红书搜索标题与已有封面标题分开，正文能讲清核心内容并覆盖搜索关键词；
- 抖音没有正文；视频号同时提供短标题、核心理论和结构化简介；
- 平台文案不是同文复制；
- 量化结果、自报收入、排名和比较性结论均有证据状态；
- `validate_package.py` 返回通过；
- 输入文件旁边只新增一份 `<输入stem>_七平台内容预览.md`，除非用户明确要求其他交付物；
- 报告生成的 Markdown 文件，但不把“内容预览生成”说成“已经发布”。
